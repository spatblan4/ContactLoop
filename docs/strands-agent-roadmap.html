Strands Agents 深挖路线图

分支：dev · 日期：2026-09-12 · 依赖：strands-agents >= 1.0.0（backend/requirements-bedrock.txt）

1. 现状与差距

项目当前对 Strands Agents SDK 的使用集中在两处：

  • 本地 Outreach Agent（backend/app/services/outreach_plan_agent.py）：单次调用、1 个工具（get_outreach_candidates）、structured output、90 秒硬超时、输出按授权候选集二次校验；
  • Contact Brief Lambda（ai/ 目录，已部署的外部服务）：Strands Agent + Bedrock，工具限定为 get_contact_stats / get_teacher_notes_and_topics / get_open_follow_ups。

SDK 的其余能力——Hooks、Guardrails、会话管理、多 Agent 模式、MCP、评测（Evals）、OpenTelemetry 可观测性——尚未使用。下表为分阶段深挖方案。

2. 总览

3. Phase 0 — 把现有 Agent 产品化 优先

目标：安全边界从「约定」变成「SDK 强制」，并让调用过程可见。

能力落点
Hooks（HookProvider / BeforeToolCallEvent）在 outreach agent 注册只读守卫 hook：拦截任何非白名单工具调用并记录。当前「agent 永不写 follow-up」只是 prompt 约定，hook 后成为代码级保证
Bedrock GuardrailsBedrockModel(guardrail_id=...) 接入内容过滤 / 话题阻断 / PII 保护；支持 shadow 模式（仅记录）先观察误杀率
OpenTelemetry 追踪Agent(trace_attributes=...) 携带 owner_id / 会话标识；spans 输出到控制台或 OTLP 端点，排查 90 秒超时的配套诊断
测试用 FakeModel实现 Strands Model 接口的假模型，使 pytest 能驱动真实 agent loop（工具选择、structured output 解析、hook 拦截），而非仅 monkeypatch generate_plan

4. Phase 1 — 会话与多轮交互

  • 多轮 Outreach 问答：teacher 看到 plan 后追问「为什么 Emma 是 high？」，agent 基于同一份授权候选事实回答；SummarizingConversationManager 控制上下文长度；
  • SessionManager 自定义存储：实现 Strands storage 接口，落在现有 SQLAlchemy 双库（SQLite / Supabase Postgres），按 teacher_id 隔离会话，AWS 部署时可切换 DynamoDB 后端；
  • SSE 流式响应：callback_handler + FastAPI StreamingResponse，把 agent 推理进度流给前端（消除 90 秒白屏等待）。

5. Phase 2 — Agent 能力扩展（按价值挑选）

owner-scoped 只读工具

每个工具都走 require_owned_* —— 工具层天然防越权，这是本项目最大的架构优势：

  • get_contact_history(student_id) / get_open_follow_ups() / get_teacher_notes(student_id)，对齐 Lambda 侧的窄工具面；
  • 语音笔记真链路：boto3 调 Amazon Transcribe 替换转录存根 → agent 生成 teacher_confirmed=false 的笔记草稿，教师确认后生效；
  • 通话后摘要：Connected 事件后从 discussed topics + 转录生成 contact-event note 草稿。

多 Agent 模式

  • Agents-as-Tools：「Teacher Assistant」协调者组合 outreach planner / 摘要器 / 问答器；
  • Swarm / Graph：草稿 → LLM-as-judge 自审 → 终稿 的质量流水线；
  • MCP：将 ContactLoop 只读数据暴露为 MCP server（IDE agent 可查询），或让 agent 消费外部 MCP 工具（如校历）——仅暴露只读面。

6. Phase 3 — 评测体系（strands-agents-evals）

  • 固定学生 fixture 构建 Case / Experiment；
  • CorrectnessEvaluator：输出是否只基于事实；InstructionFollowingEvaluator：是否遵守 priority 规则、是否输出电话号码；
  • 轨迹评测：工具调用序列是否合法；
  • 混沌测试：注入工具超时 / 网络错误，验证 fail-closed 行为；
  • 评测进 CI，用 nova-lite 控成本。

7. Phase 4 — AWS 深度集成（可选）

  • AgentCore Runtime 部署形态；A2A 协议对接学校侧系统；
  • 多 Provider：LiteLLM / Anthropic / Ollama provider，本地开发免 AWS 依赖。

8. 安全红线（贯穿所有阶段）

  • 工具一律 owner-scoped 只读：每个工具入口走 require_owned_*，跨教师数据不可达；
  • 教师确认制：agent 只产草稿（pending / teacher_confirmed=false），任何写入需教师在 UI 明确确认；
  • fail-closed：agent 超时、越权学生、结构异常一律拒绝（503），输出按授权候选集二次校验；
  • 候选上下文最小化：不含电话号码、provider ID、token、凭据；
  • 测试不触网：单测全部使用 FakeModel / monkeypatch，不真实调用 Bedrock；
  • 不可动项：Contact Brief Lambda（外部已部署，文档规定不可修改）、Twilio 拨号（Supabase Edge Function 独占）。

9. 推荐节奏

Phase 0 → Phase 1 连续落地（约一周，收益最大：安全加固 + 可观测 + 多轮交互）；Phase 2 优先「语音笔记草稿」与「工具扩展」；Phase 3 在功能稳定后补齐；Phase 4 视部署需求。
